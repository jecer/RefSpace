# Изоляция рендерера и возврат веб-безопасности

Дата: 2026-09-20
Статус: утверждён, реализация не начата

## Задача

Окно приложения создаётся с полным доступом к Node и полностью отключённой
веб-безопасностью, при этом рендерер загружает стороннее содержимое —
видеопотоки googlevideo и ответы зеркал Piped. Подменённый или
скомпрометированный ответ получает исполнение произвольного кода на машине
пользователя.

Текущее состояние (`main.js:20-37`):

| Настройка | Значение | Следствие |
| :--- | :--- | :--- |
| `nodeIntegration` | `true` | Рендереру доступен весь Node |
| `contextIsolation` | `false` | Страница и preload делят один контекст |
| `webSecurity` | `false` | Нет политики одного происхождения |
| `webviewTag` | `true` | Включён, но не используется |
| `setCertificateVerifyProc` | `c(0)` | Принимается **любой** сертификат |
| `ignore-certificate-errors` | включён | То же на уровне сети |
| `no-sandbox` | включён | Песочница Chromium выключена |

Пока RefSpace был личным инструментом, это была теоретическая проблема. Проект
опубликован и готовится к распространению подписанным установщиком, а подпись
означает для пользователя «этой программе можно доверять».

## Границы

Входит: изоляция рендерера, возврат проверки сертификатов, возврат политики
одного происхождения, удаление неиспользуемых точек расширения.

Не входит: формат файла проекта, новые возможности интерфейса, работа над
видео. Это отдельные проекты со своими спеками.

Требование: ни одна существующая возможность не теряется. Скриншот кадра
YouTube сохраняется в исходном разрешении.

## Что удаляется

Мёртвый код убирается до переноса, иначе мигрируется пустота.

- `require('fs')` и `require('path')` в `renderer.js:2-3`. Проверено: обращений
  к `fs.*` нет вовсе, а все совпадения по `path.*` — это SVG-элементы с именем
  `path` и строковые операции над локальными переменными.
- `webviewTag: true`. В проекте нет ни одного `<webview>`.
- Загрузка `https://www.youtube.com/iframe_api` в `renderer.js:1660-1663`
  вместе с `ytApiLoaded` и `onYouTubeIframeAPIReady` в `renderer.js:1654-1657`.
  YouTube рендерится
  обычным `<video>` с потоками от yt-dlp; переменная выставляется и нигде не
  читается. Это последняя сторонняя загрузка в рантайме.
- `no-sandbox`, `ignore-certificate-errors`, `setCertificateVerifyProc`.

## Preload-мост

### Почему не зеркало IPC

Очевидное решение — выставить наружу `invoke(channel, ...args)`. Оно
бесполезно: рендерер снова получает доступ ко всем каналам, и единственное, что
меняется, — синтаксис вызова. Граница должна проходить по смыслу, а не по
механике.

### Форма API

`contextBridge.exposeInMainWorld('refspace', ...)` с именованными функциями.
Каждая проверяет аргументы **на стороне main**, а не в preload: preload живёт в
том же процессе, что и страница, и границей доверия не является.

```
window.refspace = {
  project: {
    save(data, existingPath, dialogTitle),
    open(dialogTitle),
    openPath(filePath),
    startupFile(),
    fileExists(token)
  },
  window: {
    minimize(), maximize(), close(),
    setOpacity(value),            // число 0.1–1.0
    setAlwaysOnTop(flag),
    setClickThrough(flag),
    setClickThroughHotkey(key),
    onClickThroughChanged(cb),
    onOpenProjectFile(cb)
  },
  clipboard: {
    readText(), readImage(), readPureRef(),
    writeImage(dataUrl), writeItems(payload)
  },
  media: {
    pathForDroppedFile(file),     // единственное место, где нужен webUtils
    registerLocal(pathOrFile),    // -> token
    resolveYouTube(videoId)       // -> { videoToken, audioToken }
  },
  log(message)
}
```

Соответствие 14 существующим каналам — один к одному. Новых возможностей
рендерер не получает.

### Перенос clipboard и nativeImage в main

Работа с буфером обмена (`renderer.js:1439, 1440, 1905, 2048, 2216, 2591, 2598,
2615`) переезжает в главный процесс целиком. Причина техническая: при
`sandbox: true` в preload доступны только `contextBridge`, `ipcRenderer`,
`webFrame` и `webUtils`; модуля `clipboard` там нет.

Чтение формата PureRef (`readBuffer('pureref/binary')`) переносится как есть:
разбор буфера остаётся в рендерере, main отдаёт только байты.

## Протокол и одно происхождение

### Почему недостаточно просто завести схему

Страница грузится через `loadFile`, то есть её происхождение — `file://`. Если
отдавать медиа по `refspace://`, происхождения окажутся разными, canvas
останется «грязным», и три места чтения пикселей сломаются:

- `renderer.js:1435` — скриншот кадра видео
- `renderer.js:2597` — копирование картинки в буфер
- `renderer.js:2844` — вшивание картинки при сохранении проекта

### Решение

Приложение само переезжает на протокол. Страница — `refspace://app/index.html`,
медиа оттуда же, `refspace://app/_media/<token>`. Одно происхождение, canvas
чистый, заголовки CORS не нужны вовсе.

Схема регистрируется до `app.ready`:

```
protocol.registerSchemesAsPrivileged([{
  scheme: 'refspace',
  privileges: { standard: true, secure: true, supportFetchAPI: true, stream: true }
}])
```

`standard: true` обязателен — без него у схемы не будет нормальной семантики
происхождения.

### Токены вместо путей

Рендерер никогда не передаёт и не получает абсолютный путь. Когда пользователь
добавляет файл на холст, main регистрирует его и возвращает непредсказуемый
токен; обработчик протокола отдаёт только зарегистрированное. Скомпрометированный
рендерер не сможет прочитать произвольный файл с диска.

Реестр живёт в памяти и наполняется заново при открытии проекта.

## Прокси видеопотока

Проверено: googlevideo отражает `Access-Control-Allow-Origin` только для
`https://www.youtube.com`, для прочих происхождений заголовка нет. Клиентскими
средствами (`crossOrigin="anonymous"`) задача не решается, поэтому поток идёт
через главный процесс.

Ветка того же протокола: `refspace://app/_stream/<token>`.

- Токен выдаётся, когда main **сам** разрешил ссылку через yt-dlp. URL
  googlevideo рендереру не показывается и от него не принимается — иначе
  получится открытый прокси.
- Обязательна поддержка `Range`: ответ `206 Partial Content` с корректным
  `Content-Range`. Без этого сломается перемотка.
- Токен живёт, пока элемент на холсте; ссылки googlevideo и так истекают.

Главный риск проекта — именно здесь: перемотка и буферизация.

## Переключение флагов

`contextIsolation: true`, `nodeIntegration: false`, `webSecurity: true`, плюс
CSP в документе, разрешающая только собственное происхождение.

`sandbox: true` — цель с оговоркой. Доступность `webUtils` в песочнице надо
проверить на месте. Если её там нет, получение пути брошенного файла решается
иначе, и это фиксируется отдельным решением, а не откатом песочницы.

## Порядок работ

Приложение работоспособно после каждого шага.

1. Удаление мёртвого кода
2. Preload и API рядом со старым доступом; `nodeIntegration` ещё включён,
   работают оба пути
3. Перевод всех вызовов рендерера на `window.refspace`
4. `contextIsolation: true`, `nodeIntegration: false`
5. Протокол; переезд страницы и локального медиа
6. Прокси потоков
7. `webSecurity: true`, сертификаты, CSP, попытка `sandbox: true`

## Проверка

Автотестов в проекте нет, поэтому проверка ручная и обязательна после каждого
шага. Сломаться может тихо.

| Сценарий | Что проверяет |
| :--- | :--- |
| Перетаскивание картинки на холст | `webUtils`, реестр токенов, протокол |
| Перетаскивание видеофайла | То же для видео |
| `Ctrl+V` картинки из буфера | clipboard в main |
| Вставка элементов из PureRef | `readBuffer('pureref/binary')` |
| Копирование картинки с холста | Чтение пикселей, шаг 5 |
| Скриншот кадра локального видео | Чтение пикселей локального медиа |
| Скриншот кадра YouTube | Прокси и одно происхождение, шаг 6 |
| Перемотка YouTube по таймкодам | Поддержка `Range` — главный риск |
| Сохранение и открытие проекта | Вшивание картинок, диалоги |
| Двойной клик по `.mpref` | Запуск с файлом, единственный экземпляр |
| Сквозные клики по F4 | Глобальный хоткей |
| Смена языка | i18n не задет |

## Как поймём, что готово

- В `main.js` нет `nodeIntegration`, `webSecurity: false`, `no-sandbox`,
  `ignore-certificate-errors` и подменённой проверки сертификатов
- В `renderer.js` нет ни одного `require`
- Приложение не обращается ни к одному стороннему хосту, кроме разрешения
  видео через главный процесс
- Все сценарии из таблицы проходят
